# Исполняемый прототип E0

Это намеренно маленький CPU-прототип, а не production-движок и не попытка закрыть все исследовательские вопросы.

Он реализует вертикальный срез основных идей требований:

- детерминированную адресацию октантов `bx + 2*by + 4*bz` и `Derive32`;
- процедурное поле `B`, неизменяемый контекст `Γ` и наблюдаемую зависимость от исходного соседского параметра;
- разреженные результирующие правки `D` с правилом deepest-wins и `M=Resolve(B,D)`;
- материальные экземпляры с масками владения и композиционный повторный `Split` через пересечение новой маски с текущей;
- независимую физическую иерархию `FractalRing`: `Contact` без эффекта, явный `Attach`, `Detach` с наследованием скорости жёсткого движения;
- cold `Save/Load` B/D/Γ, ownership masks, material/physical IDs и физического леса;
- исполняемые тесты ключевых контрпримеров из двух независимых аудитов.

## Запуск

```bash
npm test
npm run demo
```

Зависимостей npm нет; нужен современный Node.js с `node:test` и `structuredClone`.

## Конкретные решения прототипа

Для объёма состояние корня равно `rootSeed`. В каждой ячейке ветвь определяется как `bx + 2*by + 4*bz`, где бит равен 1 для координаты на верхней половине соответствующей оси. Путь строится от корня последовательно; состояние потомка получается последовательным применением `Derive32`.

Материальный экземпляр имеет текущую ownership-mask. При повторном `Split` новая маска вычисляется как пересечение текущей маски с новой полуплоскостью. Поэтому уже отделённая материя не появляется снова.

## Сознательные ограничения

Прототип не реализует WebGPU, mesh/LOD, настоящий collision solver, автоматический fracture, Fuse, деформацию, самогравитацию, общий интегратор тензора инерции и production-формат хранения. `integrateMass()` — конечная CPU-выборка по центрам листьев уровня E0; для плоскостей, совпадающих с бинарными границами (`x=0`, `y=0`), она точна, но не является общим аналитическим интегратором.

Требования в `requirements/*.rg.yaml` остаются качественными кандидатами на русском языке. Прототип нужен, чтобы обсуждение архитектуры опиралось на исполняемое поведение, а не на бесконечное уточнение формулировок.
