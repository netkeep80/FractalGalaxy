# Studio Workspace — кандидатные требования и приёмка

**Статус:** draft/candidate, не принято Author. **База:** `c5b8eab6df091ea1b0e3124336b5d5a3702606a8`.

## Основание и классификация

Методологическая основа: К. Вигерс, Дж. Битти, «Разработка требований к программному обеспечению», 3-е изд., глава 1 (три уровня и разделение требований продукта/проекта), глава 11 (атомарность, однозначность, проверяемость), глава 17 (приёмка), глава 29 (прослеживаемость).

Требования `FG-STUDIO-*` описывают **функции и качества продукта**, поэтому выводятся из `FG-PRODUCT-000`, а не `FG-PROJECT-000`. При этом существующая принятая ветка `FG-WEB-001…008` не модифицируется без отдельного решения Author. `FG-RENDER-003…004` наследуются от принятой ветки движка и не меняют M/B/D.

Высокоуровневая возможность: пользователь исследует фрактальную материю на разных уровнях и отличает доказанную материальную поверхность от диагностических и недоказанных геометрических представлений.

## Пользовательские сценарии

### US-01 — Исследовать ячейку (Slice S1)

1. Открыть Studio и выбрать reference 3D.
2. Щёлкнуть по видимой внешней грани: определяется ячейка, показываются её адрес и сторона.
3. Перейти к родительской ячейке и заданной дочерней области; адрес меняется закономерно.
4. Повернуть камеру; прежнее выделение остаётся тем же.
5. Сменить язык RU→EN→RU; выделение, параметры и камера не изменяются.

**Отрицательные случаи:** щелчок вне области не создаёт ячейку; drag не трактуется как click; выход за диапазон depth не создаёт недопустимый путь. Поверхность в деформированном представлении может иметь иные экранные координаты; точный deformed picking не входит в S1.

### US-02 — Исследовать поверхность (Slice S2/S3)

1. Просмотреть доказанные interface patches отдельно от unresolved.
2. Включить режим собранной поверхности для доказанного локального интерфейса.
3. При переходе на региональный обзор различать доказанные участки и незакрытые/недоказанные области.
4. Не получать физическую оболочку путём эвристического заполнения `unresolved`.

## Критерии приёмки S1

- Прямой 3D picking в reference domain на глубинах 1…4 возвращает корректный canonical path; детерминированен при одинаковом viewport/camera.
- Нажатие вне проекции domain возвращает отсутствие hit.
- При навигации parent/child сохраняется пространственная вложенность и не выполняется materialization FractalRing.
- В правом inspector отображаются path, level, face, neighbor, materials и extraction stats.
- Переход RU↔EN меняет подписи без изменения selected path, camera или параметров эксперимента.
- RU/EN каталоги имеют одинаковые ключи; нет непереведённых ключей интерфейсных контролов.
- `npm test` и проверки RepoGuard exact BASE→HEAD выполняются для точного candidate SHA.

## Явные ограничения S1

- Прототип остаётся статическим GitHub Pages приложением, без серверной части.
- Уровни: selection depth, proof depth, surface refinement depth и display LOD не отождествляются.
- Изменение камеры/языка/selection не меняет `M = Resolve(B,D)`.
- Реализация точного picking деформированной поверхности, coarse/fine stitching, regional assembled mesh, fatigue и полноценной механики не заявляется завершённой в S1.

## Приоритеты

**P0 / S1:** канонический выбор 3D, переходы по иерархии, inspector, локализация, автотесты.
**P1 / S2:** визуальное разделение patches и цельной локальной поверхности.
**P2 / S3:** региональная поверхность и отдельная задача на coarse/fine LOD.

## Прослеживаемость

`derives_from` обозначает primary hierarchy parent, `implemented_by` / `verified_by` подтверждают фактическую реализацию и проверки. Не использовать `depends_on` для подмены происхождения требования. Текущий PR не устанавливает lifecycle accepted/current: это исключительное решение Author.

## US-03 — Просмотр нескольких иерархий (S1-TREE)

Источники: пользовательское требование о древовидных контролах и принятая модель различия octree, физического родительства FractalRing и процедурного происхождения. Новые требования: FG-STUDIO-012…014, кандидаты.

1. Дерево **Octree** показывает виртуальный корень Ω, раскрывает по восемь канонических дочерних октантов и позволяет выбрать узел. Выделение синхронизируется с 2D/3D и breadcrumb. При выборе через Canvas дерево раскрывает предков выбранной ячейки. Никаких FractalRing от просмотра не возникает.
2. Дерево **Split E0** отображает root → left и right → rb/rt как происхождение разделения; оно не является текущей физической иерархией. Выбор листа left/rb/rt выбирает точку внутри области владельца.
3. **FractalRing: физическая иерархия** строится только по действительным persistent records и physicalParentId. **FractalRing: процедурные источники** группирует записи по rootId + algorithmId/version + address; виртуальные адреса помечаются отдельно и не принимаются за materialized ring.
4. При отсутствии записей WorldStore деревья FractalRing показывают пустое состояние, не EMPTY материю. UNLOADED метаданные можно показывать, но ради просмотра записи не делаются RESIDENT.
5. Контролы используют RU/EN каталог, aria roles и клавиатурную навигацию. Раскрытие/collapse не меняет материал, seed, массу, камеру и постоянное состояние.

**Автоматическая приёмка:** модельные тесты уровней, количества потомков, физической/source группировки, отсутствия ложной материализации; браузерные сценарии раскрытия/сворачивания, выбора из дерева/канваса, синхронизации с inspector, смены языка и пустого FractalRing-состояния. Полное дерево не должно eagerly раскрывать `8^depth` элементов.
