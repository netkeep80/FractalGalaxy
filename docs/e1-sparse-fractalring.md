# E1 — sparse FractalRing overlay

Статус: рабочая архитектура следующего этапа. Она фиксирует новое разделение между потенциальным процедурным миром и персистентной иерархией FractalRing.

## 1. Две независимые структуры

### Процедурное адресное пространство

Octree-разбиение куба, его адреса и промежуточные состояния генератора принадлежат алгоритму фрактализации. Потенциальная область может быть вычислена по адресу без создания FractalRing.

Например:

```text
Planet:/5/2/7/3
```

может быть запрошен и вычислен целиком процедурно. Сам факт отличия результата этой области от соседних областей не создаёт persistent state.

### Sparse FractalRing overlay

FractalRing появляется тогда, когда области требуется самостоятельное сохраняемое состояние или идентичность, которых нет в чистой канонической генерации: изменение материи, явное переопределение параметров/алгоритма, отдельное владение после Split, независимое движение, Attach/Detach или иное физическое состояние.

Поэтому персистентная структура может содержать:

```text
PlanetRing
├── ChangedRegion-17   source = Planet:/5/2/7/3
├── BrokenRock-81      source = Planet:/1/6/0/4/2
└── CraterFragment-4   source = Planet:/5/2/7
```

без FractalRing для неизменённых промежуточных адресов `/5`, `/5/2` и т.п.

## 2. FractalRing не является octree-ячейкой

Octree задаёт восемь потенциальных адресов следующего уровня. Алгоритм может вычислять только нужные ветви и может вернуть EMPTY либо иной результат без создания persistent объекта.

FractalRing — владелец индивидуализированного состояния. Он может представлять часть процедурной области, ограниченную ownership-mask, и потому не обязан геометрически совпадать с одним octree-кубом.

## 3. ProceduralRef

Материализованный FractalRing сохраняет стабильную ссылку на процедурное происхождение:

```text
ProceduralRef {
    rootId
    address[]
    algorithmId
    algorithmVersion
    neighborRefs
}
```

Эта ссылка не является текущим физическим родителем. Она должна оставаться неизменной при переносе, Attach и Detach.

Процедурный родитель может вообще не иметь FractalRing. Его можно получить из адреса удалением последнего octree-индекса.

## 4. Соседи

Параметры исходных процедурных соседей разрешаются через стабильные procedural references или эквивалентный замкнутый Γ. Текущее физическое соседство не является источником генерации.

Это позволяет фрагменту, который был отделён от планеты и перемещён в другой FractalRing, продолжать уточняться в исходном контексте.

## 5. Критерий материализации

Обычная процедурная неоднородность не материализует FractalRing.

Материализация требуется, когда появляется хотя бы одно индивидуализирующее состояние, например:

- изменение материала относительно канонического результата;
- явное изменение параметров или алгоритма;
- собственная ownership-mask;
- самостоятельная идентичность после Split;
- независимое положение/скорость;
- persistent geometry displacement относительно процедурной формы;
- изменение физической композиции.

Это copy-on-write-подобная модель: процедурный мир является воспроизводимым backing state, а FractalRing overlay хранит только то, что надо сохранить отдельно.

## 6. Хранилище

Логический WorldStore разрежен и не обязан целиком находиться в RAM. Persistent existence и transient residency — разные состояния: запись может существовать в мире и одновременно быть UNLOADED.

Индексы по FractalRing ID, procedural source и physical parent должны работать на persistent уровне и не требовать загрузки payload всех rings. Допустимы memory-mapped, paged и другие backend'ы при одинаковой семантике мира.

Отсутствие FractalRing-записи означает только отсутствие индивидуализированного persistent state. Оно не означает отсутствие соответствующей процедурной области.

Подробный контракт E1 storage: [e1-world-store.md](e1-world-store.md).

## 7. Rendering

Renderer может виртуально запрашивать более глубокую фрактализацию, чем фактически материализовано в FractalRing overlay. Такие запросы не создают rings.

Процедурные surface properties и производные визуальные кэши должны строиться из той же канонической генерации с наложением sparse изменений, чтобы фактическая последующая материализация той же области не меняла её происхождение.

## 8. Текущий E1-A код

Первый slice вводит:

- `src/procedural/source-ref.mjs` — стабильные процедурные ссылки;
- `src/rings/fractal-ring.mjs` — индивидуализированный FractalRing с независимым physical parent;
- `src/storage/world-store.mjs` — единственный E1 storage API для sparse overlay и persistent-record/residency модели будущего paged/mmap backend;
- `tests/sparse-fractalring.test.mjs` и `tests/world-store.test.mjs` — минимальные поведенческие проверки.

Существующий E0 API остаётся доступен через `src/fractal-matter.mjs`.

### Порог геометрической индивидуализации

Само наличие воздействия не создаёт FractalRing.

Если geometry influence после применения material/algorithm threshold имеет нулевой результирующий offset, область остаётся процедурно воспроизводимой по geometry-признаку и не требует materialization.

Только ненулевой persistent geometry override является причиной индивидуализации по этому основанию.
