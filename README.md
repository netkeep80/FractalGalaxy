# FractalGalaxy

Экспериментальный движок **фрактальной материи**: интерактивные тела, процедурно определяемые в кубических областях, с раздельными объёмным и поверхностным уточнением.

## Центральная гипотеза

- `B` — исходная пространственная иерархия материи, детерминированно вычисляемая из `seed`, версии генератора и адреса.
- `D` — разреженная иерархия **результатов** воздействий, а не журнал действий.
- `M = Resolve(B, D)` — текущее материальное состояние. Ни GPU-меш, ни текущая глубина LOD не являются состоянием мира.
- Физические тела могут отделяться и сращиваться. Контакт и механическое соединение **не тождественны** материальному слиянию.
- `seed` наследуется дочерними областями **при фрактализации**, не при физическом отрыве. Генерация может использовать неизменяемые параметры исходных процедурных соседей после их физического разделения.
- Один самостоятельный материальный объект — `FractalRing`. При слипании создаётся новый `FractalRing`-агрегат со своей системой координат и прежними объектами как детьми, **без переопределения их seed**.
- Процедурная родословная материи не совпадает с меняющейся физической иерархией `FractalRing`.

См. [архитектурную гипотезу](docs/architecture.md), [план проверок](docs/verification-plan.md) и нативные [Requirements](requirements/).

## Стадия проекта

Только спецификация кандидата (17 нативных Requirements): **алгоритмы и физический движок ещё не реализованы**. Требования имеют `accepted: false`, `current: false` до отдельного решения Автора. Не путать RepoGuard CI с подтверждением предметной корректности.

## RepoGuard v6.0.1

Workflow в `.github/workflows/repo-guard.yml` закрепляет точный upstream commit `74db97791e6da8a75287164f0d0b41579108f114` (tag `v6.0.1`) и сравнивает exact PR `BASE/HEAD`.

**Bootstrap caveat:** исходный `main` содержит только `LICENSE` и не имеет Requirements. Точный запуск на HEAD `e17aee0a124abd6afe3ad009f646db7968ec53a7` показал: `HEAD J1 = 22/22`, `HEAD J2 = 17 rooted`, `J3 = GREEN`; единственная диагностика полной проверки — `unjustified_resource` для `LICENSE` в исходном BASE. Это RED базовой J1-closure, а не нарушение требований кандидата. Не обходить её фиктивными отношениями, отключением проверок или утверждением о GREEN. После принятия и bootstrap-merge требуются повторная проверка на новой базе и отдельная настройка required status check в GitHub branch protection/ruleset; workflow не создаёт защиту ветки автоматически.

## Ключевой эксперимент

Отделить две соседние процедурные области, удалить их прежний физический родитель, разнести фрагменты, продолжить фрактализацию с исходными граничными входами, затем объединить один фрагмент с третьим объектом через новый `FractalRing`. Результаты генерации и изменения материи остаются неизменными. См. V11–V17 в плане проверок.
